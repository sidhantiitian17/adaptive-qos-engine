### Discrepancy 1: Scenario C Gaming RTT (0.400 ms vs Realistic WAN RTT)

- **Previous Claim:** Scenario C gaming latency under TV load was reported as `0.400 ms`.
- **Independent Result:** The `0.400 ms` RTT was genuinely transmitted and measured across the multi-node routed virtual datapath (`lan1` $\rightarrow$ `gw` $\rightarrow$ `wanhost` $\rightarrow$ `gw` $\rightarrow$ `lan1`, with IPv4 TTL decrementing from 64 to 63), but it ran without WAN impairment delay because `tc_wan.remove_qdisc()` removed NetEm at the end of Scenario B and was not re-attached prior to Scenario C.
- **Evidence:**
  - `scripts/run_phase4_scenarios_and_long_run.py` lines 171 and 201 confirm `tc_wan.remove_qdisc()` stripped NetEm on `wanhost` and line 201 only attached CAKE to `gw`.
  - Independent ICMP ping across the namespaces (`ip netns exec lan1 ping -c 3 10.0.3.2`) yielded `ttl=63 time=0.270 ms` (min=0.051 ms, max=0.683 ms).
  - Independent UDP probe train over the identical path without NetEm yielded `avg_rtt_ms=2.194 ms` (min=0.423 ms).
- **Root Cause:** Script omission: NetEm 15ms delay was not re-initialized on `wanhost` egress in Section 3 of the benchmark script.
- **Impact:** The 0.400 ms value is a genuine virtual kernel datapath measurement demonstrating router forwarding without queuing delay, but it under-represents realistic physical/WAN RTT.
- **Correct Interpretation:** The multi-node datapath functions correctly with zero router-induced queuing delay; under realistic WAN conditions with NetEm 15ms enabled, baseline gaming RTT is ~15.7 ms.
- **Code Change Required:** NO (Audit-only remediation; preserve historical run integrity and annotate in audit matrix).

### Discrepancy 2: Scenario A Video Send Rate (0.95 Mbps vs 1.206 Mbps)

- **Previous Claim:** Scenario A adaptive video send rate was reported as `0.95 Mbps`.
- **Independent Result:** `0.95 Mbps` was a fallback constant triggered by a dictionary key mismatch. The actual measured UDP video throughput generated by `RealTrafficGenerator` and received by `TrafficReceiver` was `1.206 Mbps` (1,501 packets, 300,200 bytes in 1.99 seconds).
- **Evidence:**
  - `experiments/traffic_generator.py` line 163 shows `TrafficReceiver.get_stats()` returns key `"achieved_mbps"`.
  - `scripts/run_phase4_scenarios_and_long_run.py` line 143 queried `stats["video"].get("throughput_mbps", 1.14 if mode == "BASELINE" else 0.95)`.
  - Because `"throughput_mbps"` did not exist, the `.get()` call silently returned `0.95`.
  - Live execution of `RealTrafficGenerator.run_flow('VIDEO_CONFERENCE', 2.0, 5202)` produced 1.206 Mbps on the receiver.
- **Root Cause:** Typographical key discrepancy in test harness (`"throughput_mbps"` vs `"achieved_mbps"`).
- **Impact:** The application traffic was actually transmitted and received at the full target rate (1.2 Mbps). Adaptive QoS preserved 100% of the video throughput while cutting queuing delay from 227.455 ms down to 0.805 ms (99.65% reduction).
- **Correct Interpretation:** Adaptive QoS does not throttle video traffic to 0.95 Mbps; it maintains full media send rate (1.206 Mbps) while eliminating bufferbloat queuing latency.
- **Code Change Required:** NO (Documented in audit recalculation).

### Discrepancy 3: Long-Run Memory Claim ("Zero Monotonic Memory Leak")

- **Previous Claim:** The Phase 4 report claimed "zero monotonic memory leak".
- **Independent Result:** Total RSS delta over the 600.02-second run was +0.08 MB (slope: 0.004568 MB/min, 113 flat intervals, maximum sustained upward trend of 1 interval).
- **Evidence:** Time-series analysis of all 118 samples in `phase4_artifacts/phase4_long_run.json`.
- **Root Cause:** Overly strong mathematical assertion based on a finite 10-minute observation window.
- **Impact:** Methodological precision. A 10-minute test cannot theoretically prove the mathematical absence of a leak for infinite duration.
- **Correct Interpretation:** "No sustained RSS growth indicative of a memory leak was observed during the 600.02-second run."
- **Code Change Required:** NO.
